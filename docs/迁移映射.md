# ihomy → bit_pouch 迁移映射

> ihomy 工具箱是 bit_pouch 的开发与体验来源。本文记录迁移了什么、改了什么、以后怎么同步。

## 1. 迁移原则

1. **逻辑与测试优先**：`utils/*.js` 和对应 `*.spec.js` 是行为基线，先迁逻辑，再写界面。
2. **不迁外壳**：ihomy 的路由、登录守卫、Pinia 用户态、Element Plus、主题系统、后端接口一律不带入。
3. **保持错误码**：`empty`、`unexpectedChar`、`invalidBase64`、`tooLong` 等错误码保持一致，便于迁移测试直接复用。
4. **界面重写**：只保留交互意图，视觉与组件用 bit_pouch 设计系统。
5. **有意差异要记录**：若出于性能或跨端需要改变行为，写在本文件第 4 节。

## 3. 架构行为差异

| 主题 | ihomy | bit_pouch | 原因 |
|------|-------|-----------|------|
| 工具注册 | `Tools.vue` 手写数组 + 单独路由 | `import.meta.glob` 自动发现 | 新增工具零改全局文件 |
| 执行线程 | 页面内同步调用 | main/worker 由清单决定 | 大输入不阻塞 UI |
| 错误文案 | 页面 i18n 字典按 code 渲染 | run 返回本地化 message | 插件自包含，视图更薄 |
| 排序 | localStorage 用户拖拽排序 | manifest `order` | 跨端一致、无迁移成本；用户自定义留到后续 |
| 输入持久化 | 部分页面保存偏好 | 只保存选项，不保存输入 | 隐私与跨设备一致性 |
| UI | Element Plus + ihomy 主题 | 自建设计系统 | 体积、视觉控制、跨端 |
| 路由 | web history + 登录守卫 | hash history + 无登录 | 静态/Tauri/移动零配置 |
| 网络 | 依赖 ihomy 后端登录态 | 完全本地、无网络 | 工具产品定位 |

## 4. 已知功能差异

1. **JSON 自动格式化**：ihomy 需点按钮；bit_pouch 同样显式运行，避免输入半截 JSON 时持续报错。`Ctrl+Enter` 与按钮均支持。
2. **工具排序**：V0.1 不支持用户拖拽排序；按 manifest `order`。若后续恢复，需要设计跨端同步策略。
3. **JSON 高亮上限**：超过 200,000 字符关闭高亮；ihomy 同样有 200,000 上限，行为一致。
4. **字节表上限**：512 行；与 ihomy 一致。
5. **逐字表上限**：500 字符；与 ihomy 一致。
6. **报文上限**：65,536 字节；与 ihomy 一致。
7. **进制小数**：最多 16 位并标记近似；与 ihomy 一致。
8. **无 ihomy 基线的工具**：UUID / URL / Regex 以及 V0.5 的 data-format / http-message / curl-convert / ip-range / mqtt-topic 在 ihomy 中没有对应实现，测试为本项目新写；后续若 ihomy 增加同名工具，以其 spec 为基线对齐。
9. **统一格式化入口**：bit_pouch 将 JSON 与 XML / HTML 合并为 `format` 插件，自动模式以 `{` / `[` 开头识别 JSON，其余交给标记语言推断；ihomy 在线工具页同样合并为 `format` 面板，旧 `/json` / `/markup` 链接重定向到 `/format`，底层解析规则一致。
10. **Hash 旧接口兼容**：bit_pouch 原有单值 `algorithm` 选项保留，新调用使用 `algorithms` 数组；单算法结果仍带 `hex` / `base64` 字段。文本走 Worker，文件模式在主线程读取（`File` 不能跨 Worker 传递）。
11. **时间工具合并**：ihomy 的 `time` 工具并入既有 `timestamp` 插件，不新增重复的 `time` 目录；默认模式仍是时间戳转换，并保留 `milliseconds` 字段。
12. **随机生成器无降级**：全部随机数走 Web Crypto，缺失时返回 `cryptoUnavailable`，不退回 `Math.random`。
13. **JWT 合并而非新增**：ihomy 的 `jwtTool` 覆盖解码/验签/密钥/加解密，全部并入既有 `jwt` 插件；页面改为四页签，令牌与密钥不落盘。
14. **PDF 依赖按需加载**：`pdfjs-dist ^6.4.299` 只在打开 PDF 工具后动态加载，入口 chunk 不受影响；PDF 工具自身 chunk 约 437KB、worker 约 1.26MB，属于有意例外。
15. **文件与图片主线程**：`File` / Canvas 不能跨 Worker，文件与图片工具在主线程处理；ZIP 打包使用 fflate（gzip 约 8KB），图片压缩不引第三方库。
16. **Ops 数据为静态快照**：命令表来自 ihomy `opsCommands.js`，其中包含 ihomy 生产环境的端口示例（如 19068 / 6306）；bit_pouch 只展示，不读取任何环境配置。
17. **V0.5 在线面板各自实现**：ihomy 在线工具页不跨仓引用 bit_pouch 代码，`DataFormatPanel` / `HttpMessagePanel` / `CurlConvertPanel` / `IpRangePanel` / `MqttTopicPanel` 各自携带纯 JS 逻辑，行为以 bit_pouch 的 `run.spec.js` 为准；`data-format` 的 YAML / TOML 解析使用 ihomy 已安装的同源依赖，不额外引入新包。
18. **在线目录与打包工具同构**（2026-10-21）：在线目录 24 个条目与 `src/plugins/` 一一对应，`id` 等于插件目录名；`time` 在线条目改为 `timestamp`（文案沿用 `tools.time.*`），新增 `url` / `uuid` 在线面板（`urlTool.js` / `uuidTool.js` 转写），`markdown` 不再出现在 bit_pouch 在线目录（ihomy 自己的 Markdown 阅读器页不受影响）；旧链接 `/json`、`/markup`、`/time`、`/markdown` 由 ihomy 路由重定向。

## 5. 同步流程（从 ihomy 拉更新）

1. 在 ihomy 仓确认目标工具的最新实现与 spec。
2. 只复制纯逻辑与测试到对应插件；保持函数名与错误码。
3. 若接口签名变化（如 `formatJson` 返回结构），同步修改插件视图与测试。
4. 运行：

```bash
npm run check:plugins
npm test
npm run typecheck
npm run build
```

5. 若行为有意变化，更新本文件第 3、4 节与 `docs/变更归档.md`。
6. ihomy V10.58 起可用 `node scripts/export-tools.mjs --target ../bit_pouch/src/plugins` 拉取清单与核心；`time` 通过 `bitPouchId: timestamp` 落到既有插件，已存在的目录默认跳过，先比对 manifest `version` 再人工合并。`jwt` 已合并过，导出时不要 `--force` 覆盖。

## 6. 不迁移清单

- 登录/注册/家庭/权限/后端 API。
- 脑图、AI 测试台、Flash/GBA、贷款、光照等非工程或依赖外部服务的工具。PDF 已作为工程工具迁入。
- Element Plus、ihomy 主题、首页模块体系。
- 任何生产部署脚本、数据库 schema、服务器凭证。
