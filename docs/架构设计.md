# bit_pouch 架构设计

> 本文回答四个问题：系统由什么组成、一个工具从点击到出结果怎么走、为什么这样分层、以后怎么扩展。

## 1. 目标与非目标

### 目标

1. **快**：高频工具一次点击直达；输入即算不卡顿；重计算不阻塞 UI。
2. **本地优先**：默认零网络；输入内容不落盘、不上传。
3. **跨端同源**：Web/PWA、Windows/macOS/Linux 桌面、Android/iOS 共用一套工具内核与界面。
4. **插件化增长**：新增工具只加一个目录，不改路由、首页、构建配置。
5. **可验证**：纯函数逻辑与 ihomy 的行为基线对齐，单元测试覆盖边界与错误。

### 非目标

- 账号体系、云同步、多人协作。
- 服务端 API、数据库、远程插件市场。
- 富文本编辑器、文件管理、AI 对话等重业务。
- 运行时从网络下载并执行不可信远程代码；本地用户插件只接受本机源码，不在此列。

## 2. 约束

| 约束 | 影响 |
|------|------|
| 移动端与桌面端同源 | 不用依赖桌面专属 API 的工具实现；壳能力（快捷键/窗口）隔离在 Tauri 侧 |
| 离线可用 | 不依赖 CDN、远程字体、运行时网络请求；PWA 预缓存 app shell |
| 输入可能很大 | JSON/报文等工具要有上限、分片或 Worker，不能一次性渲染十万个 DOM 节点 |
| 包体积敏感 | 不引入重型 UI 库；工具视图按路由懒加载；重型依赖不得进入入口 chunk |
| 隐私 | 工具输入不写存储；插件默认无网络权限 |
| 多端交互差异 | 桌面快捷键 + 侧栏；移动端底部导航 + 大触控目标 + 安全区 |

## 3. 系统上下文

```text
┌──────────────────────────────────────────────────────────────────┐
│                            User                                  │
│              desktop / mobile / browser (PWA)                    │
└───────────────────────────────┬──────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────┐
│                    Shell (Vue 3 + Vite)                          │
│  App.vue: sidebar / topbar / bottom nav / command palette        │
│  Router: / , /t/:id , /favorites , /settings                     │
└───────────────────────────────┬──────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────┐
│                    Core (framework-agnostic TS)                  │
│  registry  ·  runner  ·  i18n  ·  theme  ·  storage  ·  toast    │
└───────────────┬───────────────────────────────┬──────────────────┘
                │                               │
┌───────────────▼──────────────┐  ┌─────────────▼──────────────────┐
│ Plugins (build-time)         │  │ Worker (single instance)       │
│ manifest.ts / run.ts / View  │  │ dynamic import run.ts by id    │
└──────────────────────────────┘  └────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────────┐
│ Platform shell                                                   │
│  Web/PWA · Tauri desktop (Window/Shortcut) · Tauri mobile        │
└──────────────────────────────────────────────────────────────────┘
```

**没有后端。** 所有计算在设备内完成；唯一的外部依赖是构建期 npm 包。图中的 Plugins 是构建期内置插件；另有运行时用户插件，源码存 localStorage，经 `new Function` 编译后并入 Registry。

## 4. 分层架构

| 层 | 位置 | 职责 | 不允许 |
|----|------|------|--------|
| Shell | `src/App.vue`, `src/views` | 导航、布局、命令面板、收藏/最近、设置 | 写具体工具算法 |
| Registry | `src/core/registry.ts`, `manifest.ts`, `userPlugins.ts` | 自动发现内置插件、加载用户插件、校验清单、搜索、懒加载 run/View | 执行计算 |
| Runner | `src/core/runner.ts`, `core/worker` | 选择 main/worker、超时、取消、错误收敛 | 关心具体工具语义 |
| Plugin runtime | `src/plugins/<id>/run.ts` | 纯函数计算，返回 `ToolResult` | 访问 DOM/存储/网络 |
| User plugin runtime | `src/core/userPlugins.ts` + 设置页 | 本机源码编译、清单补全、结果归一化、localStorage 存储 | 上传、自动下载、进 Worker |
| Plugin view | `src/plugins/<id>/View.vue` | 工具专属交互与结果呈现 | 复制算法（应调用 run） |
| Core services | `src/core/*` | i18n、主题、存储、剪贴板、平台判定 | 依赖具体插件 |
| Platform shell | `src-tauri` | 窗口、全局快捷键、单实例、移动入口 | 承载业务逻辑 |

**依赖方向**：Shell → Registry/Runner → Plugin；Plugin → Core；Core 不反向依赖 Plugin。`ToolIcon` 是唯一的“插件 id → 图标”映射点。

## 5. 插件模型

### 5.1 目录契约

```text
src/plugins/<id>/
  manifest.ts    必需。纯数据清单，供列表/搜索/排序/平台过滤。
  run.ts         必需。纯函数计算入口，导出 `run`。
  View.vue       必需。工具界面（可使用共享组件与 core API）。
  run.spec.js    建议。行为测试，迁移工具以 ihomy spec 为基线。
  README.md      建议。该工具的特殊约束与协议说明。
```

### 5.2 清单

```ts
interface ToolManifest {
  id: string                    // 与目录名一致
  name: { zh: string; en: string }
  description: { zh: string; en: string }
  category: 'codec' | 'convert' | 'inspect' | 'network' | 'text'
  icon: string                  // ToolIcon 登记的图标名
  keywords: string[]            // 搜索命中词（中英都放）
  version: string
  runtime: 'main' | 'worker'
  platforms: Array<'web' | 'desktop' | 'mobile'>
  offline: boolean
  order?: number                // 首页排序，缺省 100
  experimental?: boolean
}
```

**为什么清单是纯数据**：`registry.ts` 用 `import.meta.glob('../plugins/*/manifest.ts', { eager: true, import: 'default' })` 在构建期静态收集。若清单里 import 了视图或依赖 DOM 的模块，列表页会被迫加载所有工具代码，破坏懒加载。

### 5.3 发现与注册

```ts
const manifests = import.meta.glob('../plugins/*/manifest.ts', { eager: true, import: 'default' })
const runLoaders = import.meta.glob('../plugins/*/run.ts')
const viewLoaders = import.meta.glob('../plugins/*/View.vue')
```

- 目录名 → id；`validateManifest(folderId, manifest)` 校验形状与 id 一致性。
- `main.ts` 启动时 `assertRegistry()`：有任何清单错误直接失败，避免半残列表进入运行态。
- `loadRun(id)` / `loadView(id)` 按需动态 import；同一 id 的模块只加载一次（ESM 缓存）。
- 工具路由统一 `/t/:id`，由 `ToolView.vue` 解析 id 并动态挂载插件视图。

**用户插件（运行时注册）**：

- `main.ts` 启动时 `loadUserPlugins()` 读取 `bitpouch:user-plugins:v1`，用 `new Function` 编译成 `{ manifest, run }`，写入 `shallowRef<Map>`，与内置清单合并。
- 编译失败的记录进入 `userProblems`，只在设置页展示，不阻塞启动；安装/删除时替换整个 Map，触发 UI 重新计算。
- 用户插件复用 `/t/:id` 与 `callTool`；`loadView` 返回通用 `UserToolView`，`loadRun` 包装 `normalizeToolResult`。
- 用户插件 id 不得与内置 id 冲突；相同 id 再次安装视为更新。

**新增工具不需要改任何全局注册文件。** 这是本项目最重要的扩展性约束。

### 5.4 运行契约

```ts
type ToolRun<T = unknown> = (
  input: string,
  options: Record<string, unknown>,
  ctx: { locale: 'zh' | 'en'; signal?: AbortSignal },
) => ToolResult<T> | Promise<ToolResult<T>>

interface ToolResult<T> {
  ok: boolean
  output?: string
  error?: { code: string; message: string; line?: number; column?: number; char?: string; lineText?: string }
  stats?: Record<string, number | string>
  data?: T
}
```

约定：

- **不抛裸异常**：业务错误用 `{ ok:false, error }`；只有基础设施故障（Worker 不可用等）由 Runner 处理。
- **`output` 是人类可复制的文本结果**；结构化结果放 `data`。
- **`stats` 只放标量**，用于底部统计条。
- **`message` 已本地化**：run 根据 `ctx.locale` 生成文案，视图不再维护错误码字典。
- **幂等**：相同输入/选项必须得到相同结果；不要在 run 内读写全局状态。

### 5.5 视图

- 视图通过 `callTool(id, input, options, locale)` 调用逻辑，不直接复制算法。
- 共享组件：`Pane`、`CopyButton`、`SegmentedControl`、`StatChips`、`ErrorNote`、`ToolCard`。
- 视图负责：即时反馈、防抖、请求竞态（序号守卫）、结果渲染上限、空态/错误态。
- 选项用 `useToolPrefs(id, defaults)` 持久化；**输入内容不持久化**。

## 6. 执行模型

### 6.1 主线程 vs Worker

| 条件 | 选择 |
|------|------|
| 单次计算 < 50ms、输入通常 < 50KB | `runtime: 'main'` |
| 单次计算 > 50ms、输入可能 > 100KB 或 MB 级文本、CPU 密集 | `runtime: 'worker'` |
| 需要 DOM/Canvas/剪贴板 | `runtime: 'main'`（并在文档说明） |
| 用户插件 | 固定 `main`，不进入 Worker |

JSON 格式化与哈希使用 Worker；编码、进制、报文、子网在主线程（计算量小，避免消息复制开销）；用户插件固定主线程。

### 6.2 Worker 协议

请求：

```ts
{ requestId: number, id: string, input: string, options: object, locale: 'zh' | 'en' }
```

响应：

```ts
{ requestId: number, result: ToolResult } | { requestId: number, error: { code, message } }
```

规则：

- **单例 Worker**：避免每次计算都创建线程。单 Worker 也意味着“同一时刻一个重计算”，符合工具页的使用方式。
- **只传可结构化克隆的数据**：字符串、数字、布尔、数组、普通对象、BigInt。`Uint8Array` 会被复制（不是转移），大报文要注意内存峰值。
- **超时 30s**：超时后销毁 Worker 并重建；下一次调用重新创建。
- **取消**：`AbortSignal` 只取消主线程等待；若超时/销毁才能中断计算。
- **回退**：Worker 构造失败（老 WebView/受限环境）时回退主线程；插件抛错不回退，避免掩盖 bug。

### 6.3 为什么不用 Comlink / 复杂 RPC

- 协议只有一个方法 `run`，自写 20 行足够。
- 避免额外依赖与打包复杂度；错误码、超时、回退策略需要完全可控。
- 后续若出现流式/多方法需求，再评估升级。

## 7. 数据流与隐私

```text
用户输入
  → View 状态（内存）
  → callTool（参数）
  → run（纯函数）
  → ToolResult
  → View 渲染 / 复制
```

持久化边界：

| 数据 | 存储 | 说明 |
|------|------|------|
| 工具选项 | `localStorage: bitpouch:prefs:<id>:v1` | 缩进、进制、模板等 |
| 收藏 | `bitpouch:favorites:v1` | 工具 id 列表 |
| 最近使用 | `bitpouch:recent:v1` | 最多 8 个 id |
| 主题/语言 | `bitpouch:theme:v1` / `bitpouch:locale:v1` | 用户偏好 |
| 用户插件源码 | `bitpouch:user-plugins:v1` | 用户主动创建的本地扩展；不上传 |
| **工具输入/输出** | **不存储** | 硬性规定；插件评审必须检查 |

清理入口：设置页“清除最近使用” / “清除全部本地数据”。

## 8. 性能设计

### 8.1 加载

- 路由级懒加载：首页、工具宿主、收藏、设置分别 chunk。
- 插件视图通过 `import.meta.glob` 懒加载；清单同步收集（很小）。
- 入口只含 Vue/Router/Pinia 与壳层；`manualChunks` 把框架单独拆出。
- PWA 预缓存 app shell 与静态资源；工具代码首次使用后进入缓存。

### 8.2 计算

- JSON 解析器自写，避免 `JSON.parse` 的长整数精度丢失；输出字符串一次生成，不频繁拼接 DOM。
- 语法高亮超过 200,000 字符自动关闭，直接显示纯文本。
- 字节表最多 512 行；逐字表最多 500 字符；超出显示截断提示。
- 进制转换用 BigInt；小数按目标进制最多 16 位并标记近似。
- 报文解析上限 65,536 字节。

### 8.3 交互

- 输入防抖：编码 120ms、报文 180ms、进制 60ms、子网 90ms；JSON 显式运行（避免半截 JSON 持续报错）。
- 请求序号守卫：旧结果晚到不覆盖新结果。
- 复制按钮有成功反馈；错误就地展示，不弹远端提示。

## 9. 跨端架构

### 9.1 Web / PWA

- `vite-plugin-pwa`，`registerType: 'autoUpdate'`；图标为 SVG + 192/512 PNG + maskable。
- Hash 路由，静态托管无需服务端 rewrite。
- 剪贴板在非安全上下文可能不可用，`core/clipboard.ts` 提供 textarea 回退。

### 9.2 Desktop（Tauri 2）

- 窗口：1200×820，最小 720×520。
- 全局快捷键 `Ctrl+Shift+B`：显示/隐藏并聚焦窗口（Rust 侧注册）。
- 单实例：重复启动时聚焦已有窗口。
- 更新：`tauri-plugin-updater` + Ed25519 签名；Rust `update.rs` 维护检查 / 下载 / 安装状态机，通过 `update-status` 事件推给前端。安装包与 `latest.json` 由 Release 流水线生成，镜像只改写 URL、保留签名。
- capabilities 仅 `core:default`；新增 API 权限必须评审。
- 图标由 `src-tauri/app-icon.svg`（像素麻布袋）生成，`icons/` 目录入库；PWA maskable 使用 `app-icon-maskable.svg`（满幅背景 + 中心 80% 安全区）。

### 9.3 Mobile（Tauri 2）

- 同一前端；响应式断点 900px 切换底部导航。
- 触控目标 ≥ 34px；安全区 `env(safe-area-inset-*)`。
- `tauri android init` / `tauri ios init` 后按 Tauri 文档配置 SDK；签名材料不入库。
- 桌面专属能力（全局快捷键、单实例）用 `#[cfg(desktop)]` 隔离，移动端不编译。

## 10. 安全

- **网络最小化**：工具本身不发起请求；桌面端只在检查 / 下载更新时访问更新源（ihomy 镜像或 GitHub，可在设置页切换），不上传任何工具输入。插件若需网络，必须显式评审并在清单/文档声明。
- **输入不落盘**：见 §7。
- **更新信任链**：只接受 Ed25519 签名包，签名不符直接拒装；私钥只在 CI Secrets 或本机 `~/.tauri/`，不入库；镜像只改写 URL、保留原签名。
- **Tauri**：CSP 当前为 `null`（V0.1 便于开发）；发布前应改为严格 CSP，并逐项验证 `style-src`/`connect-src`/`ipc`。
- **权限最小化**：capabilities 只开 `core:default`；不启用 shell/fs/http 等插件。
- **不可信内容**：JSON 高亮使用 `v-for` 文本节点，不使用 `v-html`；HTML 实体工具只做转义，不渲染 HTML。
- **用户插件**：本地源码以页面权限运行，可访问 DOM/localStorage/网络，无沙箱；只面向用户自己编写或信任的代码。入口是设置页手动安装，不自动下载；严格 CSP 会阻止 `new Function`，部署方需允许 `unsafe-eval` 或关闭该能力。
- **依赖**：新增依赖需评估来源、许可证、体积与跨端支持；定期升级。

## 11. 扩展性路线

| 阶段 | 形态 | 说明 |
|------|------|------|
| V0.1 | 构建期插件 | 目录约定 + 静态 glob；类型安全、零运行时加载风险 |
| V0.2 | 构建期插件 + 插件分组 | 收藏、最近、分类、命令面板增强 |
| V0.4 | 本地用户插件 | 设置页粘贴/导入源码，`new Function` 编译后注册；无签名、无沙箱、固定主线程 |
| 后续 | 签名插件包 / 插件市场 | 需要签名、权限清单、版本兼容与 Worker/iframe 隔离 |
| 后续 | WASM/原生插件 | 大文件/高性能需求（图片、压缩、加密）通过 WASM 或 Tauri command 暴露，仍走统一 run 契约 |

**运行时不自动下载或执行远程代码**。本地用户插件是显式安装的本机源码；若做插件市场，必须引入签名、权限声明、版本约束与隔离执行环境。

## 12. 关键决策记录

| 决策 | 选择 | 理由 | 代价 |
|------|------|------|------|
| 桌面壳 | Tauri 2 | 体积小、原生 WebView、桌面/移动同一套壳 | 需要 Rust 工具链；WebView 差异需验证 |
| 前端 | Vue 3 + TS + Vite | 与 ihomy 经验一致，迁移成本低 | 无 |
| UI 库 | 不用 Element Plus | 工具型产品追求体积与视觉控制 | 需自建少量组件 |
| 插件发现 | `import.meta.glob` | 零注册、类型安全、构建期可校验 | 插件必须随包构建 |
| 用户插件编译 | `new Function` 函数体 | 同步、无 Blob/CSP 依赖；兼容 `export default` | 不支持 `import`；无模块隔离 |
| 重计算 | 单例 Worker + 自写协议 | 可控、无额外依赖 | 不支持并发多任务 |
| 路由 | hash history | 静态托管/Tauri/移动端零配置 | URL 带 `#` |
| 持久化 | localStorage + 版本化 key | 简单、跨端、无需权限 | 容量有限；只存偏好 |
| 输入处理 | 不持久化 | 隐私优先 | 刷新后输入丢失（符合工具场景） |

## 13. 迁移策略

- ihomy 的 `utils/*.js` 与 `*.spec.js` 是**行为基线**；迁移到 TS 时保持函数名、错误码、边界行为一致。
- 页面只迁交互意图，不迁 Element Plus 结构；用 bit_pouch 的设计系统重写。
- 迁移完成的判定：ihomy 原 spec 全绿 + 新视图通过手工用例。
- 明细见 `docs/迁移映射.md`。

## 14. 已知风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| Tauri 移动端 WebView 差异 | 剪贴板/输入法/滚动行为不一致 | 真机回归；优先使用标准 Web API |
| Worker 大字符串复制 | 10MB 级输入内存峰值高 | 设置上限；未来用 Transferable/流式 |
| 全局快捷键冲突 | 与其他应用抢占 | 文档说明；后续提供设置项 |
| OneDrive 同步 | 构建产物/未提交改动冲突 | `dist/`/`target/` 忽略；提交前检查 |
| 插件质量参差 | 主线程阻塞/输入落盘 | 清单校验 + 评审清单 + 测试要求 |
| 用户插件死循环 | 主线程无响应、界面卡死 | 文档声明上限；用户插件不进 Worker |
