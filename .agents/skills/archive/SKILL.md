# bit_pouch 文档归档

归档 = 把**上次归档点之后**的所有改动按内容类型分流写进对应文档，并自检。bit_pouch 的跨会话记忆靠文档承载，归档质量直接决定下个会话的工作质量。

## 触发时机

- 一个功能或修复迭代**验证通过后**执行。
- 会话可能因上下文过长失败；未归档的改动会随会话丢失。
- 不要攒批；但也不必为纯格式化/注释改动写归档。

## 第一步：划定范围

1. `git status` + `git log --oneline -15`：找出未提交改动与上次归档后的提交。
2. 对照 `docs/变更归档.md` 末尾已记录的小节，判断哪些改动已归档、哪些没有。
3. 已写文档、只差提交的改动**不要重写**，直接纳入本次归档汇报。
4. 上个会话留下的半成品（代码 + 文档都有但未提交）先读归档末尾确认完成度，**续做，别重写**。
5. 确实没有新内容 → 报告“无可归档内容”。

## 分流规则

| 内容类型 | 去处 | 注意 |
|---------|------|------|
| 版本 / 在途 / 下一步 / 基线数字 | `docs/现状.md` | 唯一状态页；工具数写 `工具 **N 个**` 格式 |
| 新规则/约定/命名（结论级） | `AGENTS.md` 对应小节 | 守 16KB 上限；只留结论 |
| 踩坑（症状/真因/取证）、机制细节、排查清单 | `docs/踩坑速查.md` 对应小节 | 按“症状 → 真因 → 对策”写，附命令 |
| 功能现状（工具能力/边界/验收/路线图） | `docs/需求设计说明书.md` 对应章节 | **就地改写为当前事实**；不写时间/版本叙事 |
| 实现记录（文件级改动/决策/验证结果/数据迁移） | `docs/变更归档.md` 末尾追加 `#####` | 唯一时序记录 |
| 插件契约/开发流程 | `docs/插件开发指南.md`、`docs/架构设计.md`、`AGENTS.md` | 三处保持一致 |
| UI/交互/视觉规范 | `docs/UI设计提示词.md` | 按现有章节插入 |
| ihomy 同步差异 | `docs/迁移映射.md` | 记录行为变化与原因 |

### 需求文档的写法

- 只改功能章节，让它等于当前代码事实。
- 不要追加“V0.x 又改成了…”，也不要标注“本次新增”。
- 删除/改变能力时，把原描述改成现在的样子。
- 判据：只读功能章节能还原系统当前全部能力，且看不出改过几次。

## 流程

1. 划定范围（见上）。
2. 先 Read 目标小节，接续现有格式与措辞。
3. 写入各文档；不确定归属的内容宁可两处各提一句，不要丢。
4. 自检：
   - 更新 `docs/现状.md`（版本 / 在途 / 下一步 / 基线）与本轮功能章节。
   - 新增 / 删除 / 改 runtime 的插件：先跑 `npm run docs:index`。
   - 跑 `npm run docs:check`：校验 AGENTS 体积与链接、工具数口径、工具索引新鲜度、现状页版本。
   - 人工确认：功能章节不出现“本次/本版/V0.x 新增”等时间叙事；契约变化时 `types.ts` / 指南 / 架构 / AGENTS 四处一致。
5. **提交**：仅在用户明确要求时执行。`git add` 只指定具体文件路径（禁止 `git add -A` / `git add .`），commit message 用 `feat:/fix:/docs: 中文摘要`。
6. **推送**：默认不推送；用户明确要求才 push。

## 边界

- 只归档**已完成并验证**的内容；进行中的工作不写文档。
- 修正过时事实（工具数量、性能数字、错误码）属于归档的一部分，发现就顺手改。
- 上一次归档只做了一半（文档写了没提交、或只提交了部分文件）→ 续做，不重写。
